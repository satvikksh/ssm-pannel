# Database design

Two logical MongoDB databases, defined in `@smm/database` and connected via `connectMongo`/`MongooseModule.forRoot`:

- **`smm_panel`** — customer panel data (used by `apps/api`).
- **`smm_license`** — central license platform data (used by `apps/license-api`, planned).

All schemas set `timestamps: true`. `getModel(name, schema, collection)` registers a model idempotently; `@smm/api` registers models via `MongooseModule.forFeature` with the string model names, so **model name** (e.g. `"User"`) is the injection key while the **collection name** is snake_case (e.g. `"users"`).

## Concurrency & integrity patterns

- **Wallet debit/credit** use optimistic concurrency: `findOneAndUpdate` on a `{userId, balance: { $gte: amount }}` condition with an in-app retry loop; the new balance is written back atomically and each mutation creates an immutable `WalletTransaction`. Never mutate a wallet balance outside `WalletService`.
- **Payment approval credit** is guarded by checking `payment.status` before crediting and setting `processedAt`; the unique `{gateway,eventId}` webhook index guarantees exactly-once processing of gateway events.
- **Order idempotency** uses the sparse unique `idempotencyKey`; duplicates are detected before debit.
- **Transactions** are available via `withTransaction(connection, fn)` for multi-document operations (e.g. order + history). Order creation deliberately avoids a cross-document transaction: it debits the wallet atomically, then creates the order document (safe because the debit is the dominating invariant).

## TTL cleanup

- `api_logs`: 30 days; `notifications`: 60 days; `payment_validations` → `license_validations`: 90 days; `audit_logs`: 400 days; `system_logs`: 30 days. BullMQ `removeOnComplete/removeOnFail` retention handles queue cleanup.
